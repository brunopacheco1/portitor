# Spike: does the transfer's destination match the data permit?

Date: 2026-11-27. A research note, no code. Every source below was read
on 2026-11-27. The maintainer decided on 2026-11-27: research only in
1.4; code in 1.5 or later, and only if this note finds a way that is not
our own invention.

## The question

The planned scenario "HDAB as permit authority" (way C in
[ROADMAP, "Ways to link data user, HDAB and holder"](../ROADMAP.md#ways-to-link-data-user-hdab-and-holder-maintainer-2026-11-23);
[scenarios/data-permits](../../scenarios/data-permits/README.md) is way
F, its first step): the HDAB only issues a data permit, as a verifiable
credential. Lux Biobank checks the permit when Schuman negotiates, then
sends the data where the permit says. Portitor can already check the
permit's claims (credential constraints). It cannot check that the
transfer's destination matches a claim in the permit.

**Result:** no specification and no product we read does this. DSP lets
the consumer name any push endpoint and does not ask the provider to
check it. DCP binds credentials to the holder's DID, not to an endpoint.
ODRL has terms that come near, but no rule says how to compare them with
a transfer. EDC evaluates no policy against the destination. The EHDS
permit names a secure processing environment (SPE) and the body that
receives the data, by name, not by an address. What can be reused is the
participant's identity: check the DID of the party that receives the
data, not a URL.

## What the specifications say

### 1. DSP 2025-1: the destination is the consumer's choice

Read from the Git tag `2025-1-err2` of
[DataspaceProtocol](https://github.com/eclipse-dataspace-protocol-base/DataspaceProtocol/tree/2025-1-err2),
`specifications/transfer/transfer.process.protocol.md`, and
`artifacts/src/main/resources/transfer/data-address-schema.json`. The
[published page](https://eclipse-dataspace-protocol-base.github.io/DataspaceProtocol/2025-1/)
loads its sections with scripts, and the fetch tool saw only the
front matter, so the Markdown sources were read instead.

- "Push Transfer": "the Provider begins data transmission to an endpoint
  specified by the Consumer using an agreed-upon wire protocol."
- Transfer Request Message: "The `dataAddress` property MUST only be
  provided if the `format` REQUIRES a push transfer." It "MUST contain a
  transport-specific set of properties for pushing the data. It MAY
  include an `endpoint`, a temporary authorization via the
  `endpointProperties` property".
- The schema's `DataAddress` requires only `@type` and `endpointType`.
- The provider must check that `agreementId` "MUST refer to an existing
  Agreement". No rule asks it to check the `dataAddress` against the
  agreement or its policy. The words "evaluate" and "enforce" do not
  appear in the transfer or negotiation chapters.

### 2. DCP v1.0.1: credentials bind to the holder, not to an endpoint

Read from the Git tag `v1.0.1` of
[decentralized-claims-protocol](https://github.com/eclipse-dataspace-dcp/decentralized-claims-protocol/tree/v1.0.1/specifications),
all eight files in `specifications/` (the
[published page](https://eclipse-dataspace-dcp.github.io/decentralized-claims-protocol/v1.0.1/)
showed only its front matter to the fetch tool).

- No file mentions a transfer endpoint, a data address or a data plane.
- Self-issued ID token (Base Protocol): "The `aud` MUST be set to the
  Verifier DID". The token is bound to the verifier, not to a URL.
- Presentation Validation: "if the specific semantics of a data space
  and credentials require cryptographic holder binding, the Verifier
  MUST assert that the `credentialSubject.id` in the Verifiable
  Credential and the DID part of the `VerificationMethod` of the
  Verifiable Presentation have the same value."
- Trust Model: mapping policies to credentials: "The exact mappings
  are dataspace-specific".

So the only binding DCP offers is credential subject = presenting DID.

### 3. ODRL 2.2: terms that come near

Read from the [ODRL Vocabulary & Expression 2.2](https://www.w3.org/TR/odrl-vocab/)
(W3C Recommendation, 15 February 2018), section 4.5, and the
[Information Model](https://www.w3.org/TR/odrl-model/), section 3.

| Left operand | Definition (quoted) | Fit for a destination |
|---|---|---|
| `recipient` (4.5.20) | "The party receiving the result/outcome of exercising the action of the Rule." Note: the right operand "must identify one or more specific Parties or category/ies of the Party." | Closest in meaning: the party that gets the data, as a DID |
| `virtualLocation` (4.5.32) | "An identified location of the IT communication space which is relevant for exercising the action of the Rule." Note: "an Internet domain or IP address range." | Could hold the endpoint's host |
| `deliveryChannel` (4.5.8) | "The delivery channel used for exercising the action of the Rule." Note: "distributed only on mobile networks." | A kind of channel, not one destination |
| `systemDevice` (4.5.28) | "An identified computing system or computing device used for exercising the action of the Rule." | A machine, identified by hardware |
| `spatial` (4.5.26) | "A named and identified geospatial area ..." | A country or region, not an endpoint |

- `odrl:transfer` is "Transfer Ownership" (3.12.2), not a data transfer.
- A right operand is a value written in the policy. ODRL does not say
  how to compare it with a credential claim or a DSP `dataAddress`;
  that is up to each implementation.
- A profile may add left operands; a processor that does not know a
  profile "MUST stop processing the policy" (Information Model 3.2, 3.3).

### 4. Eclipse EDC and Tractus-X EDC: no policy sees the destination

Read on GitHub, `eclipse-edc/Connector` `main` at `4215744`
(2026-11-27) and `eclipse-tractusx/tractusx-edc` `main` at `705412f`
(2026-11-27).

- The transfer scope `transfer.process`
  (`spi/control-plane-spi/.../policy/TransferProcessPolicyContext.java`)
  holds the participant agent, the agreement and the time. It has no
  `DataAddress`.
- `TransferProcessProtocolServiceImpl.requestedAction`
  (`core/control-plane/control-plane-aggregate-services/...`) checks the
  transfer type and validates the agreement in that scope, then only
  stores the request's `DataAddress`.
- The other scopes (`catalog`, `contract.negotiation`,
  `policy.monitor`) do not hold it either. Older EDC had a scope `provision.manifest.verify`
  (`ProvisionManifestVerifyPolicyContext`, still in tag `v0.10.0`) that
  saw the resources the consumer provisioned. It was removed with
  control-plane provisioning in PR #5444 (merged 2026-01-13).
- The EDC sample `policy/policy-01-policy-enforcement` checks a
  "location" constraint against the consumer's claims at negotiation.
- Tractus-X: scopes are `catalog`, `contract.negotiation`,
  `transfer.process` and their `request.*` forms
  (`cx-policy/.../PolicyScopes.java`). Its `JurisdictionLocation`
  function extends `ValueValidatingConstraintFunction`, which only
  checks that the right operand is well formed. The location is a term
  of the contract, not a technical check.

### 5. EHDS: the permit names the SPE and a body, not an address

Regulation (EU) 2025/327: the [EUR-Lex page](https://eur-lex.europa.eu/eli/reg/2025/327/oj)
returned an empty page to the fetch tool; the text was read from the
Publications Office's copy of the Official Journal (CELEX 32025R0327).

- Art. 68(10): the permit "shall contain" (a) the data's categories,
  specification and format, "including ... whether the electronic health
  data are to be accessed in a pseudonymised format in the secure
  processing environment"; (b) the purpose; (d) "the identity of
  authorised persons ... with access rights to the electronic health
  data in the secure processing environment"; (e) the duration; (f) "the
  technical characteristics and tools available to the health data user
  within the secure processing environment"; and (c), (g), (h). No point
  names an address.
- Art. 60(1), 68(7): holders make the data available to the HDAB.
- Art. 70: "By 26 March 2027, the Commission shall, by means of
  implementing acts, set out the templates for ... the data permit".
- Art. 73(1): HDABs "shall provide access to electronic health data
  pursuant to a data permit only through a secure processing
  environment". Art. 73(2): holders upload the data to it. Art. 72: a
  trusted health data holder may run the SPE itself.

The template is a draft: [Have Your Say initiative 16712](https://ec.europa.eu/info/law/better-regulation/have-your-say/initiatives/16712),
draft implementing regulation and annexes `Ares(2026)9764418` of
16 October 2026, feedback closed 13 November 2026, not adopted. In the
permit template (Annex II):

- point 4.5 "Health data holders notified for implementation", field
  "Body to which the electronic health data are to be made available":
  the HDAB, or, under Art. 72, a trusted holder or another body;
- point 6.1 "Secure processing environment": its name and its provider
  ("[Official name]").

No field is a URL, an endpoint or a DID. The template is a form, not a
machine-readable model.

TEHDAS2, two final deliverables:
[D6.3](https://tehdas.eu/wp-content/uploads/2026/05/d6.3-guideline-for-health-data-access-bodies-on-the-procedures-and-formats-for-data-access.pdf)
(its permit template, section 6.6: "The data granted with this permit
will be released to the SPE name", free text) and
[D7.4](https://tehdas.eu/wp-content/uploads/2026/06/d7.4-technical-specification-for-health-data-access-bodies-on-the-implementation-of-secure-processing-environments.pdf)
(SPE specification; requirement EHDSR-11: the "Health data holder MUST
upload the permitted EHD to be available in an SPE"; it does not use
DSP). We found no JSON, DCAT or verifiable credential model of a permit.

### 6. Portitor today

[ADR 0027](../adr/0027-push-transfers-and-object-storage.md), sections
1 and 2, and `crates/portitor-connector/src/receiving.rs`:

- A Portitor consumer builds `dataAddress.endpoint` as
  `{PORTITOR_PUBLIC_URL}/push/{consumerPid}` (its own connector, like
  its callback address) and writes the data into its own object
  storage: "Nothing S3-specific crosses between participants".
- The provider accepts any `https://` endpoint (ADR 0027, section 1) and
  knows the consumer by the DID in its DCP token.
- Another connector (EDC) may name an endpoint on any host.

So the destination a provider can check is the consumer's DID, or the
endpoint's host. A bucket is out of reach.

## Options that reuse something existing

| Option | What is checked | Reused | Pros | Cons |
|---|---|---|---|---|
| A. The SPE operator is the consumer | The DSP consumer's DID equals a permit claim that names the receiving body; and the consumer holds an "SPE operator" credential | DCP holder binding; Portitor's credential constraints; the template's "body to which the data are made available" | Only identity, no URL; works the same with EDC; fits Art. 73(2) (the holder uploads into the SPE) | The permit names the body by official name today, so the DID claim is ours; the permit's subject is the data user, so who presents it must be settled |
| B. ODRL `recipient` in the offer | The consumer's DID equals the right operand | An ODRL 2.2 core left operand | Standard term, plain meaning | The right operand is fixed in the offer, so one offer per SPE; the link to the permit claim is ours |
| C. ODRL `virtualLocation` | The push endpoint's host is in the right operand | An ODRL 2.2 core left operand | Checks the address itself | Evaluated at transfer against the `dataAddress`: no product does it; a host says little about who runs it |
| D. No technical check | Nothing; the SPE is a term of the agreement | Tractus-X `JurisdictionLocation` works this way | No invention | The holder trusts the consumer to send data on |

## What does not exist

- No specification binds a credential claim, a permit or an ODRL policy
  to a DSP transfer destination.
- No product we read (EDC, Tractus-X EDC) evaluates a policy against
  the transfer's `DataAddress`.
- No machine-readable EHDS permit exists. The Art. 70 template is a
  draft form; it names the receiving body and the SPE by name.

## Recommendation for 1.5 or later

Option A, if code is wanted at all: check the identity of the party
that receives the data, not its URL.

1. The provider pushes only when the DSP consumer's DID is the receiving
   body of the permit. Express this with what Portitor has: a
   credential constraint on a role credential ("SPE operator", issued
   by the authority), and a permit claim with that body's DID.
2. For push, refuse an endpoint whose origin differs from the
   consumer's `callbackAddress` origin. This is Portitor's own rule, not
   a specification; it is true for a Portitor consumer today and for
   EDC only when both are behind one public URL. Check this in the EDC
   interop scenario before deciding.
3. Do not use `virtualLocation` or a new ODRL profile term until the
   Art. 70 template is adopted and someone else uses one.

The permit claim that holds the DID is our own (the template has a name
field, not a DID). Under the maintainer's rule above (code only if it
is not our own invention), this is the part that is invention. Option
D (no check, documented) is the fallback.

## Open questions for the maintainer

1. Who negotiates in way C: the data user (Schuman) with its permit, or
   the SPE operator? DCP's holder binding means the permit's subject
   must be the party that presents it.
2. Is a permit claim with the receiving body's DID acceptable while the
   template names it by official name only?
3. Is rule 2 (push endpoint on the consumer's own origin) wanted, and
   for all push transfers or only permit-gated ones? It also narrows
   [R-17](../RISKS_AND_TECHNICAL_DEBTS.md#r-17).
4. Wait for the adopted Art. 70 template (due by 26 March 2027) before
   1.5 work starts?

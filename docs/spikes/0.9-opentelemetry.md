# Spike 0.9: OpenTelemetry in the connector

Date: 2026-11-15. Timebox: one day (took half). Scratch code was kept
outside the repository. Go/no-go gate of the 0.9 plan: before building
anything, check that OpenTelemetry fits the footprint budget the
maintainer set (at most +25% binary size and +25% idle memory against
0.8.0, start time unchanged) and passes `cargo deny`.

Result: **go**. The connector binary grows by 7.3%, idle memory by 3%
with export off and 19% with export on; start time does not change;
`cargo deny` passes.

## Set-up

- Crates (latest on crates.io, 2026-11-15): `opentelemetry`,
  `opentelemetry_sdk`, `opentelemetry-otlp` and `opentelemetry-http`
  0.33.1, `tracing-opentelemetry` 0.34.0. Features: traces and metrics,
  OTLP over HTTP with Protocol Buffers (`http-proto`); no gRPC (`tonic`),
  no reqwest, no logs signal.
- Export only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; JSON logs as
  today otherwise.
- A span per request on the public port (in `serve::with_limits`), and
  one histogram, so both signals are exported.
- Measured with `scripts/measure.sh` (`LOAD_SECONDS=10`), three runs per
  build, on the 4-core cloud container used for development: 0.8.0
  (main at b6ec467), the spike build with export off, and the same build
  with export on to a local OTLP receiver (a 15-line Python HTTP server
  that answers 200). Release profile, static musl, as the images.

## Two findings that changed the design

1. **The SDK exports from its own threads, not from tokio.** The batch
   span processor and the periodic metric reader of `opentelemetry_sdk`
   0.33 run on plain threads; hyper needs a tokio runtime. With the
   `hyper-client` feature of `opentelemetry-otlp` the connector aborted
   on the first export. Fix: a small adapter that implements
   `opentelemetry_http::HttpClient` and runs each export as a task on
   the tokio runtime captured at start. The SDK also has "experimental"
   features to run on tokio; we do not depend on experimental features.
2. **`opentelemetry-http`'s `hyper` feature switches on HTTP/2 in
   hyper for the whole build.** Cargo unifies features, so `h2` would
   have entered all three binaries, and the servers would have accepted
   HTTP/2 as well. Fix: the adapter sends with Portitor's own HTTPS
   client (`portitor_runtime::http::https_client`, HTTP/1.1, rustls with
   ring), and the `hyper` feature stays off. This alone saved 1.8 MB
   (14.1 MB with it, 12.1 MB without).

| Binary, gzip -9 (bytes) | 4,981,026 | 5,294,811 (+6.3%) | same |
| Start (ms) | 19 / 18 / 21 | 20 / 18 / 19 | 21 / 24 / 25 |
| Idle RSS (KB) | 9,100 / 9,088 / 9,084 | 9,368 / 9,360 / 9,368 (+3%) | 10,772 / 10,776 / 10,776 (+19%) |

Reading:

- Size and idle memory are within the budget, also with export on.
- Start time is unchanged within the noise of this machine.
- Throughput with export off is within the run-to-run noise (one client
  is faster than 0.8.0, 50 clients slower; base itself varies by 15%).
- With export on and **every** request traced, the connector serves
  about 20% fewer requests at saturation (50 clients, all four cores
  busy with both identities, the issuer and the load tool). Operators
  who need the throughput sample traces with OpenTelemetry's own
  `OTEL_TRACES_SAMPLER=parentbased_traceidratio` and
  `OTEL_TRACES_SAMPLER_ARG`, which the SDK reads.
- The receiver got 80 trace exports and 3 metric exports in a run: both
  signals work through the adapter.

The identity and issuer binaries get the same crates in 0.9; expect a
similar absolute growth (about 0.8 MB each).

## Dependencies

`cargo deny check` passes: advisories, bans, licences and sources ok.
With the `hyper` feature on, 21 crates were new in `Cargo.lock` (OpenTelemetry's four, `prost` and
`prost-derive`, `tracing-opentelemetry`, `async-trait`, `futures-*`,
`tokio-stream`, `tokio-util`, `itertools`, `either`, `fnv`, `anyhow`,
`portable-atomic`, `web-time`, and `h2`, which leaves again once the
`hyper` feature is off). No new duplicate versions.

## Environment variables the Rust SDK reads

Read in the sources of `opentelemetry_sdk` and `opentelemetry-otlp`
0.33.1: `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`,
`OTEL_TRACES_SAMPLER`, `OTEL_TRACES_SAMPLER_ARG`, `OTEL_BSP_*`,
`OTEL_METRIC_EXPORT_INTERVAL`, `OTEL_EXPORTER_OTLP_ENDPOINT`,
`OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_EXPORTER_OTLP_TIMEOUT` and their
`_TRACES_` and `_METRICS_` variants. `OTEL_SDK_DISABLED` is **not**
read; Portitor's switch is whether an endpoint is set. Correction found
while building (2026-11-15): the SDK's default thread-based processors
do not use `OTEL_METRIC_EXPORT_TIMEOUT`, `OTEL_BSP_EXPORT_TIMEOUT` or
`OTEL_BSP_MAX_CONCURRENT_EXPORTS`, Portitor fixes the protocol so
`OTEL_EXPORTER_OTLP_PROTOCOL` has no effect, and compression needs a
crate feature Portitor leaves off. DEPLOYING has the final list.

## Decision for 0.9

Go, with the two fixes above, as recorded in
[ADR 0023](../adr/0023-observability.md).

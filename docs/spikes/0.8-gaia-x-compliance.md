# Spike 0.8: Gaia-X compliance with a Portitor key

Date: 2026-11-15. Timebox: half a day. Scratch code was kept outside the
repository. Go/no-go gate of the 0.8 plan: before building anything, check
that a Gaia-X compliance service accepts what Portitor can sign.

Result: **go**. A local Gaia-X compliance service issued a
`gx:ParticipantComplianceCredential` for a presentation signed with a
P-256 key (ES256), the key type every Portitor component uses.

## Set-up

- Gaia-X Compliance Service **v2.16.0** (2026-11-09), image
  `registry.gitlab.com/gaia-x/lab/compliance/gx-compliance:v2.16.0`, with
  Memgraph 3.9.0, in the test mode Gaia-X documents for local testing
  ([developer-and-local-testing.md](https://gitlab.com/gaia-x/lab/compliance/gx-compliance/-/blob/development/docs/developer-and-local-testing.md)):
  `DISABLE_SIGNATURE_CHECK=true` (certificate chains are not checked
  against the Gaia-X trust anchors), `production=false` (registration
  number issuers are not checked), `USE_OFFLINE_DOCUMENT_LOADER=true`.
- `REGISTRY_URL=https://registry.lab.gaia-x.eu/v2` (gx-registry v2.14.0).
  Shapes, ontology and JSON-LD context came from
  `https://w3id.org/gaia-x/development#`, which redirects to
  `registry.lab.gaia-x.eu/development/{context,shapes,owl}/development`.
- The participant: `did:web:participant.test`, served over HTTPS, one
  `JsonWebKey2020` verification method with a P-256 `publicKeyJwk`
  carrying `alg: ES256` and `x5u` pointing to a self-signed certificate
  for the same key.
- The input followed Gaia-X's own ES256 example
  (`STANDARD_COMPLIANCE_VP_JWT_EXAMPLE` in gx-compliance
  `src/examples/signed-examples.ts`): three VC-JWTs (VC Data Model 2.0,
  `typ: vc+jwt`, `cty: vc`, headers `iss` and `kid`) for `gx:LegalPerson`,
  `gx:Issuer` (the Gaia-X terms and conditions hash) and `gx:VatID`, each
  wrapped as an `EnvelopedVerifiableCredential` in a `vp+jwt`, sent to
  `POST /api/credential-offers/standard-compliance?vcid=<id>`.

## Findings

1. **ES256 works.** The service logged "signer certificate validation
   done" and answered `201` with a VC-JWT. The service imports the key
   with `jose.importJWK`, which needs the `alg` member in the JWK (or it
   cannot tell how to use an EC key). Portitor's DID documents must add
   `alg: ES256` to the JWK.
2. **`kid` must equal the verification method's `id`** exactly (the
   service looks it up with `===`).
3. **`x5u` or `x5c` is required.** Without one the service refuses with
   "A signer DID does not contain x5u nor x5c". The certificate's public
   key must equal the JWK.
4. **The answer.** Header `alg: PS256`, `typ: vc+jwt`, `cty: vc`, `iss`,
   `kid` (the service's own `did:web`), and `iat`/`exp` in
   **milliseconds** (not seconds as JWT says, RFC 7519 section 2), so a
   verifier must take validity from `validFrom`/`validUntil` only.
   Payload: types `VerifiableCredential`, `gx:ParticipantComplianceCredential`;
   `id` = the `vcid` we asked for; subject `id` = `<vcid>#cs` (not the
   participant's DID); `gx:labelLevel: "SC"`, `gx:engineVersion: "2.16.0"`,
   `gx:rulesVersion: "CD4.0.0"`; `validUntil` = the earlier of 90 days and
   the service's certificate expiry; no `credentialStatus`.
5. **`gx:compliantCredentials`** lists each input credential by `id`,
   `gx:credentialType` and `digestSRI`. We recomputed `digestSRI` as
   `sha256-` + hex(SHA-256(JCS(the decoded VC-JWT payload))) (JCS =
   RFC 8785) and got the same three values. This is the link ADR 0022
   uses to tie the compliance credential to its holder.
6. **Network.** The service's Node.js 20 HTTP clients for JSON-LD do not
   use a proxy. Where outbound traffic must go through one, the contexts
   must be reachable directly or served locally. This matters for the CI
   job (GitHub runners have direct access) and not for operators.

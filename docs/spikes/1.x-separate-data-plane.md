# Spike: a separate, pluggable data plane

Date: 2026-11-25. A design spike, no code. Read against the 1.1 release
branch (PR #91, commit `86f4ab8`), which adds push and object storage.
The decision it proposes is [ADR 0028](../adr/0028-separate-pluggable-data-plane.md)
(Proposed).

## The question

The maintainer, 2026-11-25:

- The data plane is getting big. Moving bytes inside the connector adds
  overhead, and mixes two responsibilities.
- Operators must be able to add new data sources and new ways to
  transfer data **without changing the connector**: no new Portitor
  build, no new release, no downtime for it.
- The connector should govern data ingress and egress and the life of
  each transfer job (start, suspend, complete, terminate), not run the
  copies itself.
- Spike first, and put the work on the roadmap.

Project rules that apply: do not invent a standard; keep the number of
components small; keep the 1.x promises in [STABILITY](../STABILITY.md).

**Result:** the standard for this exists and EDC already works this
way. Data Plane Signaling (DPS) defines how a control plane registers
data planes, picks one per transfer, and drives its jobs over HTTP.
Portitor already speaks the DPS messages inside its own process. The
proposal is to serve them over HTTP as well, let operators register
their own data planes, and move the built-in data plane into its own
crate that can also run as its own image. It stays built in by default
in 1.x, because STABILITY promises the `/data` and `/push` routes on the
connector.

## What the code does today (1.1)

Data plane code in `crates/portitor-connector/src`, without tests:

| File | Lines | What it does |
|---|---:|---|
| `data_plane.rs`, `data_plane/download.rs`, `data_plane/setup.rs` | 1,400 | The built-in HTTP data plane: tokens, `GET /data/{flowId}`, reading the source (HTTP URL or `s3://`), the `DataPlane` port |
| `push.rs` | 328 | Provider push sender |
| `receiving.rs` | 516 | Consumer push receiver (`/push/{consumerPid}` into object storage) |
| `object_storage.rs`, `object_storage/*` | 1,364 | S3 client with SigV4 |
| `running_flows.rs`, `flow_membership.rs` | 469 | Cut running transfers; membership check on every use (ADR 0027, section 7) |
| `data_flows.rs`, `store/data_flows.rs` | 674 | The control plane's DPS adapter and the flow store |
| **Total** | **4,751** | 18 % of the connector's 26,555 lines |

The `portitor-dps` crate (807 lines with tests) holds the DPS messages,
the state machine and the two ports, `DataPlane` and `ControlPlane`.
They are Rust traits called in the same process
([ARCHITECTURE](../ARCHITECTURE.md#data-plane-inside-the-connector-or-separate),
[TD-17](../RISKS_AND_TECHNICAL_DEBTS.md#td-17)).

Where the data plane is tied to the control plane, beyond the DPS ports:

1. **It reads the control plane's transfer store** (`HttpDataPlane::with_transfers`)
   to name the agreement and the consumer in the audit line. DPS
   already sends both (`agreementId`, `counterPartyId`) in `start`.
2. **It calls the control plane's credential check** on every request
   and while a download or push runs (`MembershipGate`, ADR 0027,
   section 7.2). This is the largest tie: the data plane needs the DCP
   verifier, the status list cache and the trust settings.
3. **It reads the harvest's read copy** to find the dataset's source at
   each request (`UpstreamSources`). In DPS, the source travels in the
   `metadata` of `start` (EDC does this, see below).
4. **It shares the process and the SQLite file** with the control plane.
5. **The consumer side is not behind DPS at all.** The push receiver
   (`receiving.rs`) is called by the consumer transfer code directly; it
   never gets `prepare` or `started`.
6. **Data plane steps run inside the retried write of a transfer**
   ([TD-48](../RISKS_AND_TECHNICAL_DEBTS.md#td-48)). Over HTTP this
   would mean network calls inside a retry loop.
7. **Fixed in code:** two profiles (HTTP pull, HTTP push), two kinds of
   source (`https://` URL, `s3://` object). A Kafka topic, an SFTP server
   or a database needs Rust code and a new release.

So the maintainer's concern holds: today a new source or transfer type
means new development and a new release.

Two things follow:

- **The plug-in mechanism already exists and is standard:** a data plane
  is any HTTP service that implements DPS and registers its profiles.
  New transfer types come as new services, in any language, with an SDK
  in Java, Go or Rust. Nothing needs to be invented, and nothing needs a
  plug-in system inside Portitor.
- **The "gateway" role the maintainer describes also exists:** Siglet
  only grants and revokes access with tokens; the operator's own system
  serves the bytes. With registration, an operator can use such a data
  plane with Portitor without Portitor building one.

## Options

| | A. In-process plug-ins | B. DPS over HTTP, built-in stays inside | C. Like EDC: no data plane in the connector | D. B now, built-in also as its own image (recommended) |
|---|---|---|---|---|
| New transfer type without a Portitor release | No (Rust crate and rebuild), or a plug-in ABI (WASM, dynamic libraries) that no standard defines | Yes | Yes | Yes |
| Bytes leave the connector process | No | Only for external data planes | Yes | Yes, when the operator runs the separate image |
| Components to run | 3 | 3, plus any external data plane | 4 for any transfer | 3 by default; 4 when the operator chooses |
| Keeps STABILITY 1.x (`/data`, `/push`, settings) | Yes | Yes | **No**: a 2.0 change | Yes |
| Interop with EDC data planes | No | Yes | Yes | Yes |
| Work | Medium, and we own the ABI | Large | Largest | Large, plus one image |

- **A** is rejected: it fails "without changing the connector" or makes
  us define a plug-in format, which breaks the "no new standards" rule.
- **C** is where EDC is now, and probably where Portitor goes in 2.0.
  In 1.x it breaks the routes and settings STABILITY promises, and it
  makes a fourth component mandatory even for a laptop demo.
- **B** gives operators the plug-in, but leaves the built-in data plane
  tied into the connector (ties 1 to 6 above).
- **D** is B plus untying the built-in data plane: it becomes a DPS data
  plane like any other, in its own crate, that the connector either
  links in (default, same behaviour as 1.1) or reaches over HTTP when
  the operator runs it as `portitor-dataplane`.

## Recommendation: D, in four steps

Each step ships on its own and can be stopped after.

1. **Untie inside the process. No change of behaviour.**
   - The built-in data plane gets everything from DPS messages:
     agreement and counter party from `start`, the dataset's source in
     `metadata` (as EDC does), the verified claims in `claims`. No more
     reads of the transfer store or the harvest copy.
   - The control plane owns the membership check of ADR 0027, section
     7.2. On a revoked membership it sends `terminate`; the data plane
     cuts what runs. The data plane no longer needs the DCP verifier.
   - Signals go to the data plane after the transfer's write, through
     the outbox (closes TD-48). This is needed before any network hop.
   - The data plane moves to its own crate with its own tables.
   - Exit: all tests and both TCKs pass unchanged; `cargo tree` shows the
     data plane crate does not depend on the control plane crates.
2. **Signaling over HTTP, and registration.**
   - The control plane serves the DPS callbacks
     (`/transfers/{id}/dataflow/prepared|started|completed|errored`) and
     calls data planes at `{endpoint}/dataflows/...`.
   - Registration by configuration first (a file, like the datasets
     file), and `PUT`/`DELETE /dataplanes` on the management port.
   - Selection as in EDC: profile, then labels, then any.
   - Authorization: the DPS `oauth2_client_credentials` profile, and
     refuse a registration without one unless a development setting
     allows it (EDC only warns; we would be stricter, see the open
     decisions).
   - The catalog offers the formats of the registered data planes.
3. **`portitor-dataplane` image.** The same crate as a binary, signed
   and released with the other three. Optional. The consumer's push
   receiver becomes a consumer data plane (`prepare`, `started`).
4. **Prove it with others' code.** Register an outside data plane with
   Portitor (Siglet, or the Go or Java SDK sample); register
   `portitor-dataplane` with an EDC control plane; run the DPS TCK
   against `portitor-dataplane`.

## Risks

- **DPS is not final** (R-06). RC4 is three months old with no new
  tag, and the profiles and the registry are untagged. Step 1 carries no
  spec risk (nothing new on the wire); steps 2 to 4 do. Mitigation:
  follow RC4 as EDC does, record each change in the changelog.
- **A new attack surface.** The signaling API changes transfer states.
  Unauthenticated, anyone on the network who knows a transfer id can
  stop or start a flow (EDC's own warning). Mitigation: authorization
  profile required; signaling on the management port, never public.
- **"The provider can always end access" (ADR 0027, section 7) becomes
  a promise of the data plane.** Portitor can send `terminate`, but it
  cannot cut bytes inside a data plane it does not run. Mitigation: say
  so plainly in DEPLOYING; short token lifetimes; the built-in data
  plane keeps the full guarantee.
- **More moving parts for operators who choose them**: one more network
  hop and one more service to monitor. The default stays as today.
- **Effort is easy to underestimate.** Step 1 touches the transfer
  service, the outbox and the store; it is the bulk of the risk. The
  1.1 review found TD-48 in exactly this area. Give step 1 its own
  release and measure (BENCHMARKS, "Data plane") before step 2.
- **Profile names.** No registry entries exist yet. A Kafka or SFTP
  profile name is agreed in each dataspace (DPS allows this); Portitor
  only routes by the string, it does not define any.

## Open decisions for the maintainer

1. Default in 1.x: built-in data plane linked in (recommended, keeps
   STABILITY) or a separate image required (a 2.0 change).
2. Registration: configuration file and management endpoint
   (recommended), or one of them.
3. Signaling security: require `oauth2_client_credentials` and allow
   none only with a development setting (recommended), or warn only, as
   EDC does.
4. Revocation with outside data planes: accept that the guarantee of
   ADR 0027, section 7 holds only as far as a data plane honours
   `terminate`, and document it (recommended); or allow outside data
   planes only for datasets that do not need it.
5. Which release: step 1 as soon as it fits (no spec risk), steps 2 to
   4 in a later 1.x, or wait for DPS 1.0 (TD-17 said "once released").

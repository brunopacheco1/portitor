Open source · Apache-2.0 · Rust · @STATUS@

A small and fast connector.

Checked at the gate, carried across.

Portitor lets an organisation offer and use data under agreed rules, using the open standards of European dataspaces: the Eclipse Dataspace Protocol for catalogs, contracts and transfers, and the Decentralized Claims Protocol for identity and verifiable credentials. It is built to work with Eclipse EDC and Simpl-Open, and to follow the Gaia-X Trust Framework.

The name. In Latin a portitor is both the customs officer at a port, who checks goods against the rules, and the ferryman who carries them across. A connector does both.

Prototype. Portitor is in its 0.x releases and not ready for production. What works today is listed in the roadmap.

Objectives

  • Standards first

    Behaviour comes from the specifications (DSP 2025-1, DCP v1.0.1, Gaia-X Trust Framework). DSP and DCP are checked against their official conformance kits, Gaia-X against a local Gaia-X compliance service.

  • Interoperable

    Talks to Eclipse EDC connectors, tested in CI; Simpl-Open is planned. Interoperability is tested, not assumed.

  • Small and predictable

    Static binaries in empty images of a few megabytes, starting in milliseconds and using a few megabytes of memory.

  • Secure by default

    Policies that fail closed, fuzzed parsers and request limits, a short list of signature algorithms, the participant's signing key held by the identity component and not by the connector, signed releases.

  • Simple to run

    Few components, one version for all of them, configuration through environment variables.

  • Open

    Apache-2.0, decisions recorded in the open, and a public security assurance case.

Minimum functionality

What a participant can do with Portitor 1.0:

  1. Publish a catalog of datasets with usage policies (ODRL offers), harvested from where you keep them and checked against the dataspace's shapes (for example HealthDCAT-AP), and browse other participants' catalogs.
  2. Negotiate a contract for a dataset, with the policy checked on both sides.
  3. Transfer the data over HTTP through the built-in data plane (the consumer pulls it, or the provider pushes it into the consumer's object storage).
  4. Prove who you are with a did:web identity and verifiable credentials (DCP), and check the credentials of others.
  5. Issue credentials, such as dataspace membership, when you run the dataspace.
  6. Meet Gaia-X rules: hold and present Gaia-X compliance credentials.

What 1.0 keeps stable

From 1.0 on, Portitor follows Semantic Versioning: a 1.x release may add to what is listed here, and only 2.0 may remove or rename it. The full list of routes, settings and files is in STABILITY, and tests compare that list with the code.

WhatPromise in 1.x
HTTP routesEach public and management route keeps its method, its path and what its OpenAPI description says. New routes and optional fields may come, so a client must ignore fields it does not know.
Environment variablesEach listed setting (the PORTITOR_* ones and four OTEL_* ones) keeps its name and meaning: a configuration that works in 1.0 works in 1.x.
Files you writeThe datasets file, the credential definitions, the bundle, the Gaia-X participant file, keys, certificates and secrets keep working in their formats.
DatabaseA 1.x release migrates an older database at start, forward only: to go back, restore the backup taken before the upgrade.
Command lineNo arguments runs the service, health asks its readiness check, and portitor-issuer bundle build keeps its options.
ProtocolsDSP 2025-1 and DCP v1.0.1 on the public ports, at the same paths.

Not promised: metric, span and log names (each change is in the CHANGELOG), the Rust crates, error texts, development aids, and limits that are not a setting. The management API key and the data plane token are opaque: do not parse them. A management route may answer 403 in 1.x, once access can be scoped. What 1.0 does not do is in STABILITY; how to upgrade from 0.9 is in OPERATING.

Try it

Run a small dataspace on your machine: its issuer, a provider and a consumer (each a connector with its identity component) and a web server with the provider's data. A script checks that the two participants prove who they are with credentials, agree a contract and transfer a file.

You need

Docker Engine 25 or later (Docker Desktop 4.27 or later) with the Compose plugin: the images' health check uses HEALTHCHECK --start-interval, which came with Engine 25. Podman works too, see TESTING. Also git, bash, curl, jq and openssl. The demo downloads about 40 MB of images; after that it runs in about 10 seconds.

Run the demo

git clone --branch v1.1.0 --depth 1 https://github.com/brunopacheco1/portitor
cd portitor
KEEP=1 scenarios/two-party/run.sh

The script writes new keys and secrets into scenarios/two-party/run/, builds and signs the dataspace's HealthDCAT-AP bundle, starts the containers and has the issuer give both participants their credentials. Then it runs the demo steps, one line starting with == each: the provider refuses a catalog request without a token, serves its catalog checked against the bundle, agrees a contract and refuses changed terms, checks credential claims, transfers a file, and refuses a credential the issuer has revoked. The last line starts with == Done. If a step fails, the script prints FAILED and the containers' last log lines.

Look around

KEEP=1 leaves everything running. The consumer's management API is on 127.0.0.1:18091, the provider's, with its harvest jobs, on 127.0.0.1:18081:

KEY=$(cat scenarios/two-party/run/consumer/management.key)
curl -s -H "authorization: Bearer $KEY" http://127.0.0.1:18091/v1/negotiations | jq
curl -s -H "authorization: Bearer $KEY" http://127.0.0.1:18091/v1/transfers | jq
PROVIDER_KEY=$(cat scenarios/two-party/run/provider/management.key)
curl -s -H "authorization: Bearer $PROVIDER_KEY" http://127.0.0.1:18081/v1/harvest-jobs | jq

To read the provider's catalog and negotiate yourself, send the consumer the requests in the DEPLOYING, with the provider at http://provider:8080/dsp/2025-1 (did:web:provider-identity%3A8090). The HTTP interface lists every call. The Bruno collection in _http/ has the requests ready; its environments are for the set-up without Docker in TESTING.

Traces and metrics (optional)

Stop the first run (see below), then start it again with an OpenTelemetry Collector, Jaeger and Prometheus (about 220 MB more images); then Jaeger is on 127.0.0.1:16686 and Prometheus on 127.0.0.1:9090. Details in TESTING.

EXTRA_COMPOSE=scenarios/two-party/observability.yaml KEEP=1 scenarios/two-party/run.sh

Stop and clean up

Remove the containers and their data, then the keys (add --rmi all to remove the images too; with the observability stack, add -f scenarios/two-party/observability.yaml):

docker compose -f scenarios/two-party/compose.yaml down --volumes
rm -rf scenarios/two-party/run

Without KEEP=1, the script does this itself at the end.

Components

One code base and one version. Each component ships as its own small image, split by who runs it and which keys it holds (ADR 0003).

ImageDoesWho runs it
portitor-connectorCatalog, contract negotiation, transfer and data plane; harvests the datasets into a read copy and checks them against the dataspace's SHACL shapes; checks partners' credentials, also against offers that ask for credential claims or Gaia-X complianceEvery participant
portitor-identityHolds the participant's identity, keys and credentials; asks the issuer for credentials and presents them to verifiers; for Gaia-X, gets and renews the participant's compliance credentialEvery participant using DCP (optional with an external wallet)
portitor-issuerIssues and revokes credentials, such as membership, and publishes their status lists; signs and serves the dataspace's schema and vocabulary bundleThe dataspace authority only: one per dataspace

Deployment order

  1. portitor-issuer, once per dataspace, by the dataspace authority: publish its did:web document, register the participants and, if the dataspace checks metadata, publish its signed bundle of shapes.
  2. For each participant, storage: a volume for each image's database file.
  3. portitor-identity: publish the did:web document over HTTPS and get a membership credential from the issuer; for Gaia-X, give it a certificate for its key and the participant's Gaia-X data, and it gets a compliance credential from a Gaia-X compliance service.
  4. portitor-connector, pointed at the identity, the database and its datasets, trusting the issuer's DID (and, if any, the authority's bundle and the Gaia-X compliance services).

Roadmap

Short releases; each one is usable on its own. Details in the roadmap; known risks and technical debts in their own list.

  1. 0.0 Technology spike: Rust chosen; catalog slice passes the DSP conformance tests (metadata, catalog)
  2. 0.1 Repository foundations: licensing, supply-chain checks, signed releases, this website
  3. 0.2 DSP version and catalog; higher OpenSSF scores (Best Practices passing, Scorecard)
  4. 0.3 Contract negotiation
  5. 0.4 Transfer process and HTTP data plane
  6. 0.5 DCP identity and presentation; EDC interoperability test; Simpl-Open spike
  7. 0.6
    Credential issuance (portitor-issuer) and policies that check credential claims
  8. 0.7 Schema and vocabulary registry: the authority's signed bundle of shapes (HealthDCAT-AP release 8 as baseline) checks datasets and messages with Portitor's own SHACL engine; datasets harvested into a read copy
  9. 0.8 Gaia-X Trust Framework (Danube): the identity publishes the certificate chain of its key and gets and renews its Gaia-X compliance credential from a Gaia-X compliance service; offers can require that credential
  10. 0.9 Operations: health checks, traces and metrics (OpenTelemetry), a quickstart
  11. 0.10 Supply chain: cargo-vet, website trust values, upstream reports
  12. 0.11 Security hardening: threat model, fuzzing every parser, request limits, status list cache
  13. 0.12
    Interoperability with EDC, published benchmarks, and the fixes of the specification review (policy terms that are not understood are refused)
  14. 0.13 API and configuration freeze: reading a provider's catalog from the management API, the EDC test with Gaia-X compliance as a repeatable run, what 1.0 keeps stable
  15. 0.14 Release candidate for 1.0: shorter documentation, a deployment guide for operations teams, OpenSSF silver, Baseline level 1 self-assessment
  16. 1.0 Stable: the 0.14 release candidate, with no new features
  17. 1.1 Push to S3-compatible object storage; health dataspace demo, step 1
  18. 1.2 The built-in data plane in its own crate (first step to a separate, pluggable data plane); one change of behaviour: a transfer keeps the data source it started with
  19. 1.3 Purpose and data permit in policies; demo, step 2
  20. 1.4 Data user and health data access body; the demo answers its four questions
  21. 1.5 Keys in OpenBao; revoked credentials leave presentations by themselves
  22. 1.6 Users and applications in the data plane; consent
  23. 1.7 EHDS data holder: dataset descriptions with the minimum metadata of the EHDS (HealthDCAT-AP), data quality and utility label
  24. 1.8 Tests against Simpl-Open: the protocol, then joining through its Tier 2 gateway
  25. 1.9 EHDS data user and HDAB: permit life cycle, data requests, hand-over to a secure processing environment, opt-out research
  26. 1.10 Hand-over to HealthData@EU: research, then an ADR
  27. 1.x Code quality, spread over the 1.x releases: one shared core for negotiation and transfer, smaller files, simpler types, a Helm chart
